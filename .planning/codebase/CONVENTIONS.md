# Coding Conventions
**Analysis Date:** 2026-07-10
## Naming Patterns
**Files:** `snake_case.py` (e.g. `project_repository.py`, `risk_analyzer.py`, `langfuse_tracer.py`).
**Functions:** `snake_case` (e.g. `get_by_id`, `load_test_projects`, `build_risk_analysis_prompt` in `app/repositories/project_repository.py`, `scripts/test/test_data_loader.py`, `app/services/risk_calculator/risk_analyzer.py`).
**Variables:** `snake_case` (e.g. `evidence_ratings`, `project_score`, `all_chunks` throughout `app/`).
**Types:** Two parallel hierarchies:
- Database models: Beanie `Document` subclasses in `app/core/models.py` (`Project`, `SourceDocument`, `Chunk`, `RiskType`, `RiskDimensionSpec`, `EvidenceRating`, `Evidence`, `RiskAssessment`, `ProjectScore`, `ProcessingState`) — PascalCase.
- Internal business types: `@dataclass` classes in `app/core/types.py` (`Project`, `Chunk`, `RiskType`, `SourceDocument`, `Evidence`, `RiskAssessment`, `ProjectScore`, `ProcessingState`, plus LLM response types `LLMRiskAnalysisResponse`, `LLMEvidence`, `LLMDimensionRating`) — PascalCase.
- Disambiguation alias pattern: `from app.core.models import Project as ProjectModel` and `from app.core.types import Project as ProjectType` (see `app/repositories/project_repository.py:3-4`, `app/core/types.py:6-9`).
- Constants are UPPER_SNAKE_CASE (e.g. `MAX_RETRIES`, `RETRY_DELAY`, `BATCH_SIZE` in `app/services/risk_calculator/risk_analyzer.py:17-21`).
## Code Style
**Formatting:** No formatter config present — no `pyproject.toml`, `ruff.toml`, `.flake8`, `setup.cfg`, or `black` config in the repo (verified via glob and grep). 4-space indentation is used consistently. Dependencies are version-pinned in `requirements.txt` (e.g. `fastapi==0.109.1`, `beanie==2.0.0`, `pydantic>=2.7.0,<2.9.0`).
**Linting:** No linter configured (no ruff/flake8/mypy config found). No type-checking enforced in CI.
## Import Organization
**Order:** Standard library first (`os`, `sys`, `json`, `typing`, `asyncio`), then third-party (`beanie`, `pydantic`, `fastapi`, `boto3`, `langchain_*`, `apscheduler`), then local `app.*` modules. All imports are at the top of each module, per `CLAUDE.md` ("All imports at top of the file. No imports inside functions or classes") — confirmed in `app/core/models.py:1-4`, `app/repositories/evidence_repository.py:1-8`, `app/services/api/routers/risk.py:1-12`.
**Path Aliases:** Absolute imports rooted at the `app` package: `app.core.models`, `app.core.types`, `app.repositories.<entity>_repository`, `app.services.api.routers.risk`, `app.services.risk_calculator.risk_analyzer`. `from x import Y as Z` aliasing is used for model/type disambiguation. One exception: `app/services/doc_parser/doc_parser.py:10` performs `sys.path.append(...)` before local `app.*` imports (module level, still above first usage).
## Error Handling
**Patterns:**
- Broad `try/except Exception` blocks that swallow errors and return safe fallbacks (`None` or empty collections) while logging via `print` — e.g. `app/repositories/project_repository.py:11-16` (`get_by_id` returns `None`), `app/services/risk_calculator/risk_analyzer.py:40-42` (`get_all_risk_types` returns `[]`).
- Critical failures `raise` after logging — e.g. `app/core/llm_service.py:31` raises `ValueError` when API key missing, `app/core/llm_service.py:68-70` re-raises after printing, `app/core/database.py:43-45` re-raises connection failure.
- Retry with constants for external (LLM) calls: `MAX_RETRIES = 3`, `RETRY_DELAY = 1` in `app/services/risk_calculator/risk_analyzer.py:17-18`, applied in `analyze_with_retry` (`risk_analyzer.py:240-312`) using `asyncio.sleep` and `asyncio.gather(..., return_exceptions=True)`.
- Resumable processing tracked via a `ProcessingState` model (`app/core/models.py:247-293`) and `ProcessingStateRepository`, with `status` (`pending`/`in_progress`/`completed`/`failed`), `error_message`, and `retry_count` (e.g. `risk_analyzer.py:332-377`).
- `FileNotFoundError` is caught specifically in fixture loaders with a graceful skip — `scripts/test/test_data_loader.py:126-128,157-159,188-190` etc.
## Logging
**Framework:** No `logging` module or `loguru` is used anywhere (grep for `import logging`/`from loguru` returned no matches). The codebase uses `print()` statements with emoji prefixes (success, error, warning, trace, DEV mode, database, LLM). Examples: `app/core/database.py:42,44`, `app/core/llm_service.py:41,69`, `app/services/risk_calculator/risk_analyzer.py:36,41,205,279`, `app/core/langfuse_tracer.py:16,26,30,33`.
**Patterns:** Emoji-prefixed progress and error messages are printed at every pipeline stage. LLM observability is centralized in `app/core/llm_service.py` and routed through Langfuse via `app/core/langfuse_tracer.py` (`get_langfuse_callback`, `get_langchain_callbacks`). Langfuse is silently skipped when keys are missing or the package is absent (`langfuse_tracer.py:15-17,29-34`). Per `CLAUDE.md`, all LLM interactions go through `llm_service.py` with Langfuse tracing; no direct LLM calls elsewhere.
## Comments
**When to Comment:** Minimal and self-documenting, per `CLAUDE.md` ("Minimal Comments — Write self-documenting code. Only add comments when the logic is unavoidably complex"). Comments appear only to explain non-obvious logic, e.g. `app/repositories/evidence_repository.py:69-70` (in-memory Link-field filtering rationale), `app/core/models.py:116-118` (why dimensions are scored then averaged), `app/core/types.py:66` (ObjectId extraction from DBRef). No block comments describing "what" — only "why".
**JSDoc/TSDoc** (or docstring usage): Python docstrings (triple-quoted) are used on public functions/classes and module headers. Module docstrings appear in `app/core/data_loader.py:1-5`, `scripts/test/test_setup.py:2-5`, `app/repositories/__init__.py:1-3`. Function docstrings describe purpose and return values, e.g. `app/repositories/evidence_repository.py:15,47,53`, `app/services/risk_calculator/risk_analyzer.py:25,168,214,241`. Dataclasses use class-level docstrings (e.g. `app/core/types.py:194,203,213`). No formal docstring linting is enforced.
## Function Design
**Size:** Functions are moderately sized but some are large — e.g. `build_risk_analysis_prompt` (`risk_analyzer.py:49-132`, ~80 lines building an LLM prompt), `analyze_with_retry` (`risk_analyzer.py:240-312`), `load_test_project_scores` (`test_data_loader.py:262-297`). Most repository and helper functions stay short.
**Parameters:** Consistent type hints on all parameters (e.g. `async def get_by_id(project_id: str) -> Optional[ProjectType]` in `project_repository.py:11`). Keyword/optional args used for defaults (`session_id: Optional[str] = None` in `llm_service.py:49`). Long parameter lists appear in pipeline orchestration (e.g. `analyze_chunk_for_risk_type` in `risk_analyzer.py:315` takes 9 positional args for progress logging).
**Return Values:** Strongly typed returns — `Optional[T]`, `List[T]`, or concrete types. Async functions return awaitables (`async def ... -> T`). Repository methods return internal `app.core.types` dataclasses (never Beanie models directly), converted via `.from_model(...)` (e.g. `project_repository.py:14`, `evidence_repository.py:49,88`). Functions frequently return counts (`int`) for pipeline reporting (e.g. `save_evidences_to_database` returns saved count, `risk_analyzer.py:167`).
## Module Design
**Exports:** Repository classes are stateless with all methods as `@staticmethod` (no instance state, no `__init__`) — e.g. `app/repositories/project_repository.py:8-37`, `app/repositories/evidence_repository.py:11-102`. Service modules expose module-level `async` functions (e.g. `app/services/risk_calculator/risk_analyzer.py`, `app/core/data_loader.py`). LLM access is funneled through a module-level singleton via `get_llm_service()` (`llm_service.py:126-130`).
**Barrel Files:** `__init__.py` files contain only a docstring and do NOT re-export members — e.g. `app/repositories/__init__.py:1-3`, `app/services/api/routers/__init__.py`, `app/core/__init__.py`. There is no `__all__`; consumers import directly from concrete modules (e.g. `from app.repositories.project_repository import ProjectRepository`).
